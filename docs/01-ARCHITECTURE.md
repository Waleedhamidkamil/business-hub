# 01 - Architecture

The big-picture map of **Business Hub** (formerly "ABRAJ Documents Hub" / "PO Tool"). Read this after [[README]] and before opening any source file. Every subsystem has its own doc - this page ties them together and lists what breaks what.

## What the app is
A **Windows desktop application** (single user, offline) for generating and tracking four kinds of business documents: **Purchase Orders, Quotations, Delivery Notes, and Invoices**. (A fifth, **Official Letters**, was retired on 2026-08-27 - never used, zero rows in either profile - so anything in git history describing "five parallel slices" now means four.) Since 2026-07-14 it hosts **two isolated company profiles** - **Abraj** and **Eshraqat** - switchable at runtime from the dashboard; each profile has its own SQLite DB, settings, brand assets, documents root, numbering scheme, and print skin (see [[13-PROFILES-BRANDS]]). It generates polished PDFs by rendering HTML through a headless browser, and adds costing/profit tracking, a dashboard with analytics, client profiles, and a data-manager for bulk maintenance.

It is **not a web server**: there is no Flask, no HTTP, no ports. It is a [pywebview](https://pywebview.flowrl.com/) window (Edge WebView2) showing a local HTML/JS app that talks to Python through an in-process bridge.

## The bridge contract (how the two halves connect)
- The frontend never imports Python; it calls **`api().<method>(...)`** where `api = () => window.pywebview.api`.
- pywebview exposes every **public method of `backend.api.Api`** by its exact snake_case name. `api().save_quote(q)` → `Api.save_quote(self, q)`. Arguments/returns are JSON-serialized automatically.
- There is **no type checking across the bridge** - a renamed or removed `Api` method silently breaks its JS caller. See the method catalogue in [[02-BACKEND-CORE]].
- Boot: `app.py` → `webview.start()`; JS runs `bootstrap()` on the `pywebviewready` event (or immediately if the bridge is already present after an F5). See [[05-FRONTEND-SHELL]].
- **Office server (2026-10-22):** the same `Api` also runs on a server, one process per logged-in person (`server/engine.py`), behind one door (`server/gateway.py`). On each PC `launcher/` shows the server's screens and its bridge forwards every call; the nine calls that act on a PC (open / print / show / copy a PDF, the pickers, the launch card) are done by the launcher. The screens are unchanged. See [[18-OFFICE-SERVER]].

## The five parallel document types
The core design is **four near-identical vertical slices**. When you add or change behavior for one, the same change usually applies to all four. Each column is a place to look:

| Concern | PO | Quotation | Delivery Note | Invoice |
|---|---|---|---|---|
| Numbering | `po_numbering.py` | `quote_numbering.py` | `dn_numbering.py` | `inv_numbering.py` |
| Generator (HTML+PDF) | `pdf_generator.py` | `quote_generator.py` | `dn_generator.py` | `inv_generator.py` |
| Print template | `po_page.html` | `quote_page.html` | `dn_page.html` | `inv_page.html` |
| DB tables | `pos` | `quotes`,`quote_items` | `dns`,`dn_items` | `invoices`,`inv_items` |
| Editor JS / view | `app.js` `editorView` | `quote.js` `quoteView` | `dn.js` `dnView` | `inv.js` `invView` |
| Browse view | `openView` | `quoteOpenView` | `dnOpenView` | `invOpenView` |

Details of what is **shared vs. duplicated** across these four are in [[04-BACKEND-DOCGEN]] - e.g. `quote_generator.py` is the canonical source of `amount_in_words` (imported by `dn_generator.py` and `inv_generator.py`); `inv_generator.py` also imports its `_money` / `_num`, while `dn_generator.py` and `pdf_generator.py` define their own copies of those two.

## End-to-end flows
1. **Create a document.** Editor JS gathers form + item-grid rows → `api().get_next_<type>_number(...)` (scans the on-disk folder tree for the max used number) → `api().preview_<type>(...)` renders a temp preview PDF → `api().save_<type>(...)` writes the DB row(s) and renders the PDF into a per-type day folder → it now appears in the browse view and dashboard. Folder shapes differ per type: QUT/INV nest `<Type>/<Client>/<Year>/<MONTH>/<DD-MM-YYYY>/`, DN nests `<Client>/<Year>/<MONTH>/<DD-MM-YYYY>/`, and PO nests `<Year>/<MONTH>/<DD-MM-YYYY>/` (no client folder).
2. **Settings resolution.** `config.py` merges built-in defaults with the user's `data/settings.json` (+ per-doc-subtype overrides) into `current_effective_settings()`; generators and `doc_settings.js` read from it. See [[09-DATA-MODEL]].
3. **Costing & analytics.** Per-item costs live in each document's own private cost column and its `doc_cost_meta` currency; they feed `analytics.py`'s `dashboard_analytics` (KPIs, funnels, signed ratio, deltas). (The separate `costing.js` workspace was retired 2026-09-11; the data and the columns were not.) See [[03-BACKEND-DATA]] + [[07-FRONTEND-SUPPORT]].

## Cross-cutting concerns
- **Company profiles & brands** - `profile_manager.py` + the profile branches everywhere: per-profile DB/settings/assets/documents-root, `_apply_company_profile_defaults()` in `config.py`, permanent Eshraqat numbering (`profile_numbering.py`), brand skins (`templates/eshraqat/` + `eshraqat_print.css`), the shared autocomplete DB (`shared_library.py`), and the `switch_profile` → `_reload_profile_runtime` reload dance. **Config values bind at import** - see [[13-PROFILES-BRANDS]] before touching any path, prefix, or identity constant.
- **Settings/config** - `config.py` (+ the ACTIVE profile's `settings.json`); affects every generator's header/logo/company identity. Per-profile since 2026-07-14.
- **Numbering & on-disk layout** - the `*_numbering.py` modules define the folder convention *and* derive the next number by scanning the filesystem. See [[09-DATA-MODEL]].
- **Column widths** - generators compute column schemas and rebalance widths to a fixed total; persisted in `doc_columns`, edited live by `col_resize.js`, and consumed by the print templates' `width: {{ c.width }}%`. A three-way agreement.
- **Per-document layout metadata** - saved docs can override defaults independently of type settings. `doc_meta.key='layout'` currently stores `autofit_rows` for PO/QUT/DN/INV; editor toggles, API payloads, and generator `autofit` resolution must agree.
- **Signing** - `signing.py` overlays signatures/stamp with randomized placement, persisted per document. See [[04-BACKEND-DOCGEN]].
- **Migrations** - `migrations.py` runs on every launch and MUST stay idempotent. See [[03-BACKEND-DATA]].
- **PDF engine** - `pdf_engine.py` finds Chrome/Edge via the Windows registry; no browser ⇒ no PDF.
