# Startup performance plan

Goal: reduce the delay to a usable dashboard without changing document behavior.

Measured baseline, three fresh processes against SQLite snapshots: dashboard
ready in 2.71-2.78 seconds. Backend setup is about 0.24 seconds, including
profile integrity checks, database setup and migrations. WebView2/.NET setup
and page loading account for most of the remaining time. About 35 animation
bridge requests run during startup and queue ahead of dashboard data, because
all API calls share the profile-switch lock. Repeated icon slugs are requested
separately for buttons on the four editors.

- [x] Add behavioral tests for concurrent animation request reuse, independent
  animation data per host, retry after failure, and dashboard-first scheduling.
- [x] Share one pending request per bundled animation slug, clone each result
  for Lottie's per-host mutation, and discard failed requests for retry.
- [x] Start the existing dashboard, toolbar and theme animations after the
  dashboard data has settled and had an opportunity to paint. Keep static SVGs,
  reduced-motion behavior, profile locking and all document flows intact.
- [x] Compare repeated real WebView2 starts against the same snapshots, verify
  both company profiles and all animations, and run the focused tests, the JS
  suite and both backend smoke tests with the test lock held.
- [x] Record the unused-file audit and measured limits. Commit only this
  change's hunks, preserving the other agent's current working changes.

No subagents, live-data cleanup or removal of migration/integrity checks.
